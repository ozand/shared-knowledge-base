# Предметно-ориентированное проектирование (DDD)

## 1. Введение
**Domain-Driven Design (DDD)** — это подход к разработке программного обеспечения, который фокусируется на моделировании предметной области (Domain) и бизнес-логики. Главная цель DDD — создать единое понимание бизнеса между разработчиками, доменными экспертами и заинтересованными лицами, устранив разрыв между реальными бизнес-процессами и программным кодом.

Вместо того чтобы отталкиваться от структуры базы данных или выбранного фреймворка, архитектура приложения в DDD строится вокруг *Модели предметной области*.

## 2. Основные концепции

### Единый язык (Ubiquitous Language)
Фундамент DDD. Это язык, который совместно разрабатывается программистами и экспертами предметной области.
* **Идея:** Термины в коде (названия классов, методов, переменных) должны строго соответствовать терминам, которые используют бизнес-эксперты в реальной жизни.
* **Преимущество:** Исключается путаница и "трудности перевода" между бизнесом и IT.

### Ограниченный контекст (Bounded Context)
Большие системы невозможно описать одной единой и непротиворечивой моделью.
* **Идея:** Вся система разбивается на независимые подсистемы (контексты). Например, в E-commerce это могут быть контексты "Каталог", "Оформление заказа", "Биллинг" и "Доставка".
* Каждый контекст имеет свои четкие границы, а внутри него понятие может иметь свой специфический смысл. (К примеру, "Покупатель" в контексте Каталога — это просто предпочтения и корзина, а в контексте Биллинга — это финансовые реквизиты).

## 3. Элементы модели (Тактический DDD)

* **Сущность (Entity):**
  Объект, имеющий уникальную идентичность, которая не меняется на протяжении всего его жизненного цикла, даже если меняются его атрибуты (например, Клиент, Заказ).
* **Объект-значение (Value Object):**
  Объект, описывающий некую характеристику, но не имеющий уникального идентификатора. Измеряется только набором своих атрибутов, и он **иммутабелен** (неизменяем). Примеры: Адрес (Улица, Дом, Город), Деньги (Сумма, Валюта).
* **Агрегат (Aggregate):**
  Кластер Сущностей и Объектов-значений, которые рассматриваются как единое целое для изменения данных. У агрегата есть "Корень" (Aggregate Root) — единственная Сущность, через которую внешние объекты могут взаимодействовать с элементами внутри агрегата.
* **Службы (Domain Services):**
  Хранят бизнес-логику, которая не вписывается в рамки одной Сущности или Объекта-значения (например, перевод средств с одного счета на другой). В них нет собственного состояния.

## 4. Пошаговый алгоритм применения DDD

1. **Изучение бизнеса:** Общение с доменными экспертами, сбор бизнес-сценариев.
2. **Формирование Единого словаря (Ubiquitous Language):** Создание глоссария терминов.
3. **Выделение контекстов (Strategic Design):** Определение Ограниченных контекстов (Bounded Contexts) и архитектурных границ между ними (Карта контекстов).
4. **Моделирование логики (Tactical Design):** Внутри каждого контекста выделение Сущностей, Агрегатов и Объектов-значений.
5. **Реализация:** Написание кода, где доменная логика полностью абстрагирована и изолирована от инфраструктуры (баз данных, API, UI) — чаще всего применяется Чистая или Гексагональная архитектура.


## Практические примеры и референсы для элементов DDD

Чтобы лучше понять тактические шаблоны DDD (Entity, Value Object, Aggregate, Domain Service) и стратегические (Bounded Context), разберем их на конкретных примерах кода на Python.

### 2. Основные концепции (Дополнения)

#### Bounded Context (Ограниченный контекст) и Ubiquitous Language (Единый язык)
**Пример из жизни (E-commerce):**
Слово **"Товар" (Product)** имеет совершенно разный смысл для разных отделов.
* В контексте **"Каталог"** Product — это название, описание, фотографии, характеристики (вес, цвет).
* В контексте **"Склад" (Inventory)** Product — это SKU, габариты полочного хранения, количество на полке. 
* В контексте **"Биллинг" (Billing)** Product — это идентификатор налоговой ставки, цена и скидка.

В правильной архитектуре мы НЕ делаем один гигантский класс `Product` на 150 полей. Мы создаем 3 разных Bounded Contexts, и в каждом из них класс `Product` имеет лишь те поля, которые в этом контексте необходимы. Это позволяет трем командам независимо развивать свои модули, используя при этом бизнес-термины (Ubiquitous Language) в коде без пересечений.

### 3. Элементы модели (Тактический DDD) с примерами кода

#### 1. Entity (Сущность)
У Сущности **есть уникальный идентификатор (ID)**. Два объекта с одинаковым ID — это один и тот же объект, даже если их свойства (имя, статус) различаются. 

**Пример на Python:**
```python
import uuid
from dataclasses import dataclass, field

@dataclass
class User:
    # Уникальный ID — главный признак Entity
    id: uuid.UUID = field(default_factory=uuid.uuid4)
    email: str = field(default="")
    is_active: bool = field(default=True)

    def __eq__(self, other):
        if not isinstance(other, User):
            return False
        return self.id == other.id

    def __hash__(self):
        return hash(self.id)
```
*Референс:* Клиент, Заказ у которого меняется статус (Created -> Paid -> Shipped), Товар.

#### 2. Value Object (Объект-значение)
Объект-значение **не имеет ID**. Его уникальность определяется **набором всех его атрибутов**. Если хотя бы один атрибут меняется — это уже другой объект. Они должны быть **иммутабельными** (неизменяемыми) и замороженными (frozen). Если нужно поменять значение — создается новый объект.

**Пример на Python:**
```python
from dataclasses import dataclass

@dataclass(frozen=True)  # frozen=True делает объект иммутабельным
class Money:
    amount: float
    currency: str

    def __add__(self, other):
        if self.currency != other.currency:
            raise ValueError("Currencies must match")
        return Money(self.amount + other.amount, self.currency)

# Два объекта с одинаковыми значениями равны друг другу:
m1 = Money(100, "USD")
m2 = Money(100, "USD")
print(m1 == m2)  # True, хотя в памяти это разные объекты
```
*Референс:* Дата и время, Адрес доставки, Гео-координаты, IP-адрес. 

#### 3. Aggregate (Агрегат) и Aggregate Root (Корень агрегата)
Агрегат — это кластер из Entity и Value Objects, которые должны меняться **вместе**, следуя общим бизнес-правилам. Взаимодействие с базой данных происходит **только через Корень Агрегата**.

**Пример:** Агрегат `Order` (Заказ) включает в себя сущность `Order` (как Корень) и список `OrderLine` (строк заказа). Нельзя добавить строку заказа в обход самого заказа, так как заказ должен пересчитать финальную сумму или проверить, не закрыт ли он уже.

```python
@dataclass
class OrderLine: # Сущность внутри агрегата
    product_id: uuid.UUID
    qty: int
    price: Money

@dataclass
class Order: # Aggregate Root
    id: uuid.UUID
    lines: list[OrderLine] = field(default_factory=list)
    status: str = "OPEN"

    # Бизнес-логика живет внутри агрегата (Rich Domain Model), а не в контроллерах!
    def add_item(self, product_id: uuid.UUID, qty: int, price: Money):
        if self.status != "OPEN":
            raise Exception("Cannot modify closed order")
        
        # Проверяем, есть ли уже товар, суммируем qty или добавляем новую линию
        existing_line = next((line for line in self.lines if line.product_id == product_id), None)
        if existing_line:
            existing_line.qty += qty
        else:
            self.lines.append(OrderLine(product_id, qty, price))
```

#### 4. Domain Service (Служба домена)
Когда бизнес-логика не принадлежит конкретной сущности и требует взаимодействия нескольких агрегатов, она выносится в Domain Service. Это функции "без состояния".

**Пример:** Перевод денег с одного счета (Агрегат 1) на другой (Агрегат 2).
```python
class BankAccount:  # Aggregate Root
    def __init__(self, id, balance: Money):
        self.id = id
        self.balance = balance

    def withdraw(self, amount: Money):
        if self.balance.amount < amount.amount:
            raise Exception("Insufficient funds")
        self.balance = Money(self.balance.amount - amount.amount, self.balance.currency)

    def deposit(self, amount: Money):
        self.balance = Money(self.balance.amount + amount.amount, self.balance.currency)

# Domain Service: логика затрагивает два независимых агрегата
class TransferService:
    @staticmethod
    def transfer(from_account: BankAccount, to_account: BankAccount, amount: Money):
        # 1. Снимаем средства
        from_account.withdraw(amount)
        # 2. Зачисляем средства
        to_account.deposit(amount)
```

### 4. Пошаговый алгоритм применения DDD (Дополнение: Event Storming)

На начальных этапах чаще всего применяется метод **Event Storming (Штурм событий)**, созданный Альберто Брандолини. Это интерактивный подход для моделирования домена. 

**Шаги Event Storming:**
1. Выписать на оранжевые стикеры **Domain Events (События)** в прошедшем времени: "Заказ создан", "Оплата отклонена".
2. Добавить на синие стикеры **Commands (Команды)** — действия пользователя, которые привели к событию ("Создать заказ", "Оплатить").
3. Добавить желтые стикеры с **Aggregates (Агрегатами)**, на которые воздействуют Команды.
4. Разбить доску на зоны — это и будут **Bounded Contexts (Ограниченные контексты)**.

*(Референсный источник по реализации DDD на Python: архитектурная книга **"Architecture Patterns with Python"** от Гарри Персиваля и Боба Грегори).*


## 5. Когда применять, а когда нет

✅ **Когда использовать DDD:**
* Проект имеет сложную бизнес-логику (много правил, зависимостей и состояний).
* Доменные правила часто меняются.
* Проект разрабатывается в течение длительного времени большой командой разработчиков и бизнес-экспертов.
* Вы строите масштабируемую архитектуру на базе микросервисов (Bounded Contexts идеально ложатся на микросервисы).

❌ **Когда НЕ использовать DDD:**
* Простые приложения типа CRUD (Создать, Прочитать, Обновить, Удалить) — блоги, витрины, базовые админки.
* Технические проекты, где нет "бизнеса" (например, драйверы, скрипты парсинга, утилиты синхронизации данных).
* Краткосрочные проекты / MVP с ограниченным бюджетом: накладные расходы на проектирование моделей при DDD слишком высоки.
